# 08. gstack이 정규식으로 섹션 제목을 찾는 이유

## 질문

gstack에서 정규식으로 섹션 제목을 찾는 이유는 무엇인가?

## 결론

이 검사는 **Claude 자신이 한 일을 Claude의 판단에 맡기지 않으려고** 기계적으로 만든 것이다. 검사 대상은 "에이전트가 명세를 고쳐서 일을 끝낸 것처럼 만드는 행동"이다. 이것을 같은 에이전트에게 판정하게 하면 판정 자체를 믿을 수 없다. 그래서 프로그램이 같은 입력에 항상 같은 결과를 내는 방식(정규식 + 텍스트 비교)으로 만들었다.

gstack 문서에 "왜 정규식인가"를 직접 적은 문장은 없다. 아래는 설계 문서와 코드 구조에서 확인한 내용이다.

## 근거

### 1. 검사가 막으려는 행동

근거: `docs/designs/HONEST_WORK_GATE_INTEGRITY.md`

이 설계 문서는 에이전트가 검증을 약하게 만드는 행동들을 다룬다. 테스트를 지우거나 건너뛰기, 시간 제한 늘리기, 실행하지 않은 명령을 실행했다고 말하기, 그리고 "명세를 고쳐서 일을 끝내기"(RH-10)가 여기에 속한다. 문서는 문제점으로 "기계적인 검사가 없다"는 점과 "자기 보고(self-report)를 믿는 구조"를 여러 번 지적한다.

### 2. 판단과 검사를 나눈 구조

근거: `ship/sections/plan-completion.md.tmpl`, `scripts/resolvers/plan-gates.ts`

`/ship` 8단계의 계획 대조는 두 부분으로 나뉜다.
- **하위 에이전트(판단):** 계획 문서를 읽고 항목마다 DONE, CHANGED, NOT DONE 등으로 분류한다. 문서의 의미를 이해해야 하므로 Claude가 한다. 한국어 문서도 이해한다.
- **상위 작업(검사):** 완료 기준 섹션이 바뀌었는지는 하위 에이전트에게 묻지 않고 직접 계산한다. 코드 주석은 이것을 "parent-computed"(상위 작업이 계산함)라고 부른다.

검사 과정은 다음과 같다.
1. 기본 브랜치에 있는 계획 문서(기준선)와 작업 중인 계획 문서를 준비한다.
2. 각 문서에서 정규식으로 완료 기준 섹션만 잘라 낸다. 제목이 `Acceptance`, `Success criteria`, `Verification`, `Test plan`, `Testing`, `Done when`, `Definition of done`으로 시작하는 섹션이다.
3. 잘라 낸 두 부분을 `diff`로 비교한다. 다르면 `ACCEPTANCE_EDITED`를 표시한다.

### 3. 섹션 제목으로 범위를 자르는 이유

계획 문서 전체를 비교하면 구현 메모나 변경 이력을 추가해도 걸린다. 03번에서 본 것처럼 gstack은 변경 이력을 덧붙이는 것을 권한다. 그래서 "약속에 해당하는 부분", 즉 완료 기준 섹션만 비교해야 한다. 섹션 제목이 그 경계를 정하는 가장 단순한 표시다.

### 4. 기계 검사의 장점과 대가

장점:
- 같은 입력에 항상 같은 결과가 나온다. 설득하거나 해석을 바꿔서 통과시킬 수 없다.
- 모델을 호출하지 않으므로 비용이 없고 빠르다. `ARCHITECTURE.md`의 테스트 원칙("문제의 95%는 무료로 잡고, LLM은 판단이 필요할 때만 쓴다")과 같은 방향이다.

대가(설계와 코드에 한계로 적혀 있다):
- 정해진 영어 키워드로 시작하는 제목만 찾는다. `## 완료 기준`은 찾지 못한다(04번 확인 섹션).
- 계획 문서가 git 밖에 있으면 기준선이 없어 비교하지 못한다.
- 계획 문서를 처음 커밋할 때 이미 고친 내용은 볼 수 없다.

## 사용자 상황에 적용할 때

- 기준: **스스로 한 일을 스스로 판정하면 안 되는 검사는 기계적으로 만든다. 의미를 이해해야 하는 판단은 Claude에게 맡긴다.**
- 이 기준을 쓰려면 문서에 기계가 알아볼 표시가 필요하다. 예를 들어 완료 기준 섹션의 제목을 정해진 형태로 쓰는 식이다. 문서 양식을 정할 때 "어떤 제목을 고정할지"도 함께 정해야 한다.
