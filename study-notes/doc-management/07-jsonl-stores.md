# 07. gstack의 JSONL 기록: 용도, 동시 쓰기, 순서, 계산 방식

## 질문

- gstack은 JSONL 파일을 주로 어떤 목적으로 쓰는가? 한 파일을 동시에 고치면 줄 순서가 문제가 되는가? 여러 에이전트가 동시에 읽고 써도 문제가 없다는 말이 사실인가?
- 프로그램이 JSONL의 필드로 계산하는 동작은 어떻게 진행되는가?
- `decisions.jsonl`과 `learnings.jsonl`을 쓰는 목적은 무엇이고, 기록을 추가하는 순서와 읽는 순서는 어떻게 되는가?

## 결론

- gstack은 JSONL을 **시간이 지나며 쌓이는 기록**에 쓴다. 세션을 넘어 기억할 것, 작업 이력과 감사 기록, 검사 결과가 여기에 해당한다.
- **파일 안의 줄 순서는 계산 결과에 영향을 주지 않는다.** 프로그램은 줄의 위치가 아니라 줄 안의 필드(`id`, `supersedes`, `date`, `ts`)로 계산한다.
- "동시에 써도 깨지지 않는다"는 말은 **줄 단위 기록에 대해서는 대체로 사실**이다. 하지만 예외가 있다. 결정 기록의 요약 파일(`decisions.active.json`)은 동시에 쓰면 잠시 최신 결정 하나가 빠질 수 있다. 05번에서 이 예외를 말하지 않았으므로 여기서 바로잡는다.

## 1. JSONL을 쓰는 곳

gstack 코드에서 이름이 나오는 JSONL 파일은 40개가 넘는다. 용도로 묶으면 다음과 같다.

| 용도 | 예 |
|---|---|
| 세션을 넘어 기억하기 | `decisions.jsonl`(결정), `learnings.jsonl`(교훈), `question-log.jsonl`, `eureka.jsonl`, `builder-profile.jsonl`, `timeline.jsonl` |
| 작업 이력과 감사 기록 | `egress.jsonl`(외부 전송 영수증), `browse-audit.jsonl`, `skill-usage.jsonl`, `ship-calls.jsonl`, `attempts.jsonl` |
| 검사 결과 모으기 | `findings.jsonl`(리뷰 지적 사항), `trial-outcomes.jsonl`(평가 결과), flake 기록 |

공통점은 **기존 내용을 고치지 않고 새 줄을 덧붙이는 기록**이라는 것이다.

## 2. 동시 쓰기와 읽기

근거: `lib/jsonl-store.ts`, `lib/gstack-decision.ts`, `bin/gstack-learnings-log`

### 쓰기: 줄이 섞이지 않는 이유

결정 기록은 `appendJsonl()`로, 교훈 기록은 셸의 `echo ... >> 파일`로 덧붙인다. 둘 다 파일을 추가 모드(O_APPEND)로 열고, 한 줄을 한 번의 쓰기로 붙인다. 추가 모드에서는 운영체제가 "파일 끝 찾기"와 "쓰기"를 한 동작으로 처리한다. 그래서 두 에이전트가 동시에 써도 각자의 줄이 파일 끝에 차례로 붙고, 한 줄 안에 다른 줄이 끼어들지 않는다.

코드 주석은 이 근거로 PIPE_BUF(한 번에 나뉘지 않고 쓰이는 크기, 보통 4096바이트)를 든다. 엄밀히 PIPE_BUF 보장은 파이프에 대한 것이고, 일반 파일에서는 Linux와 macOS 로컬 파일 시스템의 실제 동작이 근거다. 다음 경우에는 보장이 약해진다.
- 한 줄이 아주 길 때. 주석도 "PIPE_BUF보다 큰 기록은 보장을 잃는다"고 경고한다.
- 네트워크 파일 시스템(NFS)처럼 추가 모드를 제대로 지원하지 않는 곳.

### 읽기: 쓰는 도중에 읽으면

읽는 쪽은 파일 전체를 읽고 줄마다 JSON으로 해석한다. 해석에 실패한 줄은 건너뛴다(`readJsonl`). 그래서 쓰는 도중의 반쪽 줄을 만나도 전체 읽기가 실패하지 않는다. 그 줄은 이번 읽기에서만 빠지고 다음 읽기에서 보인다.

### 줄 순서는 중요하지 않다

- 결정 기록은 "어떤 결정이 대체됐는가"를 `supersedes` 필드로 판단한다. 대체 표시가 파일의 앞에 있든 뒤에 있든 결과가 같다. 결과 정렬도 `date` 필드로 한다.
- 교훈 기록은 같은 `key`+`type`이 여러 줄 있으면 `ts`(기록 시각)가 가장 늦은 것을 고른다. 파일 위치가 아니다.

예외가 하나 있다. 결정을 대체하면서 새 결정을 함께 적을 때는 **새 결정을 먼저, 대체 표시를 나중에** 쓴다. 중간에 끊기면 "옛 결정과 새 결정이 둘 다 유효"한 상태가 된다. 이 상태는 다시 실행하면 복구할 수 있다. 순서가 반대면 옛 결정만 사라지고 새 결정을 잃을 수 있다. 계산 결과를 위한 순서가 아니라 중간에 끊겼을 때를 위한 순서다.

### 문제가 생길 수 있는 곳

| 상황 | 결과 | gstack의 대응 |
|---|---|---|
| 두 에이전트가 거의 동시에 결정을 기록 | 원본 기록은 안전하다. 요약 파일은 늦게 끝난 쪽이 덮어쓰므로 다른 쪽 결정이 빠질 수 있다. 세션 시작 때는 요약 파일을 읽으므로 그 결정이 잠시 보이지 않는다. | 따로 막는 장치는 없다(코드를 읽고 판단한 것이며, 실제 사고 기록은 찾지 못했다). 다음 기록이나 `--rebuild-snapshot` 때 원본에서 다시 만들어져 바로잡힌다. |
| 정리(`--compact`) 중에 새 기록이 추가됨 | 정리가 파일을 다시 쓰면 새 기록이 사라질 수 있다. | 잠금 파일로 정리를 하나씩만 실행한다. 다시 쓰기 직전에 파일 크기가 변했으면 정리를 취소한다. |
| 두 컴퓨터의 기록을 git으로 합침 | 원본 기록은 잘 합쳐진다. 요약 파일은 충돌한다. | 요약 파일은 합치지 않고 합쳐진 원본에서 다시 만든다. |
| 컴퓨터마다 시계가 다름 | `date`와 `ts`로 정렬하고 고르므로 순서가 어긋날 수 있다. | 따로 막는 장치는 찾지 못했다. |

## 3. 필드로 계산하는 과정

### 결정 기록

1. **유효한 결정 계산** (`computeActive`): 모든 줄을 읽는다. `kind`가 `supersede`나 `redact`인 줄의 `supersedes` 값을 "물러난 id 목록"에 넣는다. 그다음 `kind`가 `decide`이면서 물러난 목록에 없는 줄만 남기고 `date` 순으로 정렬한다.
2. **범위 거르기** (`filterByScope`): `scope`가 `repo`면 항상 포함한다. `branch`면 지금 브랜치와 같을 때만, `issue`면 지금 이슈와 같을 때만 포함한다.
3. **요약 파일**: 1번 결과를 `decisions.active.json`에 저장한다. 세션 시작 때 기록 전체를 다시 계산하지 않으려는 것이다.

예시:

```
줄1 {"id":"a1","kind":"decide","decision":"Redis 큐","date":"11-01"}
줄2 {"id":"c3","kind":"decide","decision":"DB 테이블 큐","date":"11-10"}
줄3 {"id":"b2","kind":"supersede","supersedes":"a1","date":"11-10"}
→ 물러난 id: {a1} → 유효한 결정: c3
```

### 교훈 기록

1. 모든 줄을 읽는다. `key`나 `type`이 없는 줄은 버린다.
2. **신뢰도 감소**: 사용자가 직접 말한 교훈(`source: user-stated`)이 아니면 30일마다 신뢰도를 1점씩 낮춘다.
3. **중복 정리**: `key`+`type`이 같으면 `ts`가 가장 늦은 줄만 남긴다.
4. **거르기와 정렬**: 종류와 검색어로 거른 뒤, 검색어가 맞은 수, 신뢰도, 최신 순으로 정렬한다.

## 4. decisions.jsonl과 learnings.jsonl

두 파일 모두 `~/.gstack/projects/<프로젝트>/`(저장소 밖 개인 공간)에 있다.

| | decisions.jsonl | learnings.jsonl |
|---|---|---|
| 목적 | 오래 유지할 결정과 그 이유. 다음 세션이 같은 결정을 말없이 다시 논의하지 않게 한다. | 작업 중 알게 된 패턴, 함정, 선호. 다음 작업에서 같은 실수를 피하게 한다. |
| 쓰는 도구 | `gstack-decision-log` | `gstack-learnings-log` |
| 쓰는 순서 | ① 필수 값, 범위, 숨은 지시문, 비밀 값 검사 → ② `id`, `date` 자동 부여 → ③ 한 줄 덧붙이기 → ④ 요약 파일 다시 만들기 → ⑤ 다른 컴퓨터와 동기화 대기열에 넣기 | ① 종류, key 형식, 숨은 지시문, 비밀 값 검사 → ② `ts` 자동 부여, 사용자가 직접 말한 것이면 `trusted: true` → ③ 한 줄 덧붙이기 → ④ 동기화 대기열에 넣기 |
| 대체 방식 | 지우지 않고 `supersede` 줄로 대체 표시 | 같은 `key`+`type`으로 새 줄을 쓰면 최신 것이 이긴다 |
| 읽는 시점 | gstack 스킬이 시작될 때 `gstack-context-recovery`가 범위에 맞는 최근 유효 결정 5개를 보여 준다 | gstack 스킬이 시작될 때 항목 수와 상위 3개를 보여 준다. 스킬 중간에도 주제어로 검색한다. |
| 읽는 순서 | 요약 파일을 읽는다(없으면 원본에서 다시 만든다) → 범위 거르기 → 최근 것부터 | 원본 전체를 읽는다 → 신뢰도 감소 → 중복 정리 → 거르기 → 정렬 |

## 사용자 상황에 적용할 때

- 덧붙이기만 하는 기록은 동시에 쓰는 사람이 있어도 안전하게 만들 수 있다. 줄의 위치가 아니라 기록 안의 값(번호, 대체한 번호, 날짜)으로 판단하면 된다.
- 원본 기록과 거기서 만든 요약을 나누면, 요약이 틀어져도 원본에서 다시 만들 수 있다. 이것도 02번의 "원본 하나, 나머지는 생성" 기준과 같다.
