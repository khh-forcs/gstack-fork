# 문서 관리 체계 학습 기록

gstack 저장소가 문서와 폴더 구조를 어떤 기준과 의도로 만들었는지 질문과 답으로 확인하고, 그 결론을 기록한다. 목표는 gstack 구조를 복사하는 것이 아니라, 판단 기준을 이해해서 사용자의 분석·설계·구현 작업에 맞는 문서 관리 체계를 직접 설계하는 것이다.

이 파일에는 사용자 상황, 기록 방식, 목차, 결정 현황만 둔다. 내용은 주제 파일에 둔다.

## 사용자 상황

| 대상 | 위치 | 관리 방식 |
|---|---|---|
| 기획 산출물 | 별도 git 저장소 (접근 가능) | git 버전 관리 |
| 코드 | 코드 git 저장소 | git 버전 관리 |
| 개발 중 문서 (분석·설계 메모 등) | 개인 공간, 코드 git 밖 | 개인이 관리 |
| 최종 문서 | docx, 위키 | 개발 완료 후 정해진 양식으로 새로 작성 |

- 혼자 작업과 팀 작업이 섞여 있고, 문서는 필요할 때 공유한다.
- 분석·설계·구현 단계에서 Claude를 사용한다.

## 기록 방식

- 주제 하나에 파일 하나를 쓴다. 같은 주제의 후속 질문은 그 파일에 덧붙이고, 새 주제는 새 파일을 만든다.
- 파일 하나가 200줄을 넘거나 두 주제를 다루게 되면 나눈다.
- 각 기록에는 결론, 근거(gstack의 어느 파일에 무엇이 있는지), 사용자 상황에 적용할 때의 판단을 쓴다. 대화 과정은 쓰지 않는다.
- 파일 이름은 `번호-영문-주제.md` 형식으로 짓는다.
- 사용자가 한 질문은 [questions.md](questions.md)에 순서대로 모으고, 답변 항목을 주제 파일로 연결한다. 이 질문 목록은 대화마다 적용 여부를 묻는다.

## 결정 현황

| 번호 | 결정할 것 | 왜 정해야 하나 | 상태 |
|---|---|---|---|
| D1 | 개발 중 문서를 어디에 둘지 (코드 저장소 안 / 개인 폴더 / 별도 git 저장소) | Claude가 작업 중에 읽을 수 있는지, 변경 이력이 남는지가 여기서 갈린다. | 미정 |
| D2 | 최종 문서(docx, 위키)의 원본을 무엇으로 할지 (개발 중 문서에서 변환 / 직접 다시 작성) | 옮겨 쓰는 수고와 내용 누락 위험이 달라진다. 회사 양식이 자동 변환을 허용하는지 먼저 확인해야 한다. | 미정 |
| D3 | 개인 문서를 공유 문서로 옮기는 시점과 기준 | 기준이 없으면 문서가 개인 공간에 묻힌다. | 미정 |
| D4 | 기획 → 설계 → 구현 결과물을 서로 어떻게 연결할지 | 세 단계 결과물이 서로 다른 저장소와 공간에 있어서, 구현이 어떤 기획 요구에서 나왔는지 추적하기 어렵다. | 미정 |
| D5 | 소통 규칙 파일을 어디에 둘지 | 새 대화마다 읽혀야 한다. | 결정: 두 저장소의 작업 브랜치 `.claude/rules/clear-communication.md`. PR은 만들지 않고 이 세션에서 `/clear`로 이어 간다. |
| D6 | 질문과 답의 기록을 어디에 둘지 | `/clear`를 하면 대화 내용이 사라진다. | 결정: gstack-fork 작업 브랜치의 이 폴더. 주제별로 파일을 나눈다. |
| D7 | 구현 중 알게 된 사실을 분석·설계 문서에 어떻게 반영할지 (원문을 고침 / 원문을 두고 변경 기록을 덧붙임) | 원문을 고치면 예전 내용과 바꾼 이유가 사라진다. 문서가 git 밖에 있으면 되돌릴 방법도 없다. 03번 기록 참고. | 미정 |
| D8 | 사용자가 한 질문을 어떻게 모을지 | 나중에 어떤 질문을 했고 답이 어디 있는지 찾아보기 위해서다. | 결정: `questions.md`에 번호, 질문 내용, 답변(주제 파일 링크)을 쌓는다. 답변은 지금처럼 매번 주제 파일에 기록한다. 새 대화마다 이 규칙을 적용할지 묻는다. |
