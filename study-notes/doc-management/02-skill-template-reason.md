# 02. SKILL.md.tmpl 템플릿 형식을 쓰는 이유

## 질문

gstack은 왜 SKILL.md를 직접 쓰지 않고 SKILL.md.tmpl 템플릿에서 생성하는가?

## 결론

사람이 판단해서 쓰는 글과 코드에서 뽑아야 하는 정보를 나누기 위해서다. 이렇게 나누면 스킬 문서가 실제 코드와 어긋나지 않는다.

## 근거

근거: `ARCHITECTURE.md`의 "SKILL.md template system" 섹션

구조는 다음과 같다. 사람은 `SKILL.md.tmpl`에 글과 `{{자리표시}}`를 쓴다. `scripts/gen-skill-docs.ts`가 소스 코드에서 값을 읽어 자리표시를 채운다. 그 결과가 Claude가 실제로 읽는 `SKILL.md`이다.

이 방식을 쓰는 이유는 네 가지다.

1. **문서가 코드와 어긋나지 않게 한다.** 손으로 관리하는 문서는 결국 코드와 달라진다. 명령어 표와 플래그 목록을 소스 코드에서 직접 만들면, 코드에 없는 명령은 문서에 나올 수 없다.
2. **여러 스킬이 같은 문구를 한 곳에서 관리한다.** 시작 절차, 브랜치 감지 같은 공통 블록을 한 곳에 두고, 고치면 모든 스킬에 반영된다.
3. **여러 AI 도구와 모델용 문서를 한 원본에서 만든다.** Claude, Codex, Gemini 등 도구마다 경로와 모델이 다르다. 손으로 관리하면 도구 수만큼 사본이 생긴다.
4. **설치 환경과 문서 크기를 조절한다.** 설정에 따라 내용을 빼거나 나누고, 너무 큰 문서는 경고한다.

생성 결과도 저장소에 커밋한다. Claude는 스킬을 불러올 때 빌드 없이 바로 SKILL.md를 읽기 때문이다. 또 CI가 "템플릿만 고치고 다시 생성하지 않은 실수"를 잡을 수 있고, git 이력으로 변경 시점을 추적할 수 있다.

이 방식 때문에 지켜야 하는 규칙이 있다. 원본만 고치고 생성 결과는 직접 고치지 않는다. 원본과 결과를 함께 커밋한다. 충돌이 나면 원본에서 해결하고 다시 생성한다.

## 사용자 상황에 적용할 때

- 핵심 기준은 "사람이 고치는 원본은 하나, 나머지는 원본에서 만든다"이다.
- 사용자는 개발이 끝난 뒤 docx와 위키를 손으로 다시 쓴다. 이 과정이 gstack이 피하려는 "사본을 손으로 관리하는 상황"에 해당한다. 개발 중 문서를 원본으로 삼고 최종 문서를 거기서 만들 수 있는지가 결정 현황 D2의 핵심 질문이다.
