# 06. 설계 변경이 처리되는 흐름: 바뀌는 파일 순서와 호출하는 스킬 순서

## 질문

- 사용자 행동에 따라 변경되는 파일들만 처리 순서대로 보여줘.
- 사용자 행동에 따라 호출하는 스킬을 순서대로 보여줘.

## 결론

04번의 회원가입 예시를 시간 순서로 다시 놓으면 세 구간으로 나뉜다.

1. **구현 중:** 사용자가 행동하는 즉시 바뀌는 파일이 있다. 결정 기록과 설계 문서다.
2. **`/review`:** 계획과 실제의 차이를 교훈 기록에 남긴다.
3. **`/ship`:** 나머지를 한 번에 처리한다. CHANGELOG 조각, TODOS, 문서 점검, 커밋, push, PR 설명이다.

구현 중에 따로 부르는 스킬은 없다. 결정 기록은 실행 중인 gstack 스킬의 공통 지침에 따라 Claude가 남긴다.

## 바뀌는 파일 순서

| 순서 | 시점 | 사용자 행동 / 단계 | 바뀌는 파일 | 위치 |
|---|---|---|---|---|

| 2 | 구현 중 | (선택) 변경 이력 작성 | `docs/designs/SIGNUP.md` 끝에 `## Revisions` 추가 | 저장소 |
| 3 | 구현 중 | 완료 기준을 200ms → 500ms로 수정 | `docs/designs/SIGNUP.md`의 `## Acceptance criteria` | 저장소 |

- "개인 공간"은 `~/.gstack/projects/<프로젝트>/`이다. 저장소 밖이라 커밋되지 않는다.
- 순서 0의 설계 문서는 `docs/designs/`(저장소, 공유) 대신 `~/.gstack/projects/<프로젝트>/*-design-*.md`(개인 공간)에 있을 수도 있다. `/office-hours`가 만드는 설계 문서는 개인 공간에 생긴다.
- 순서 2는 도구가 하지 않는다. 사람이나 Claude가 직접 쓰는 관례다.

## 호출하는 스킬 순서

| 순서 | 단계 | 스킬 | 하는 일 (이 예시와 관련된 것) |
|---|---|---|---|
| 1 | 기획 | `/office-hours` | 아이디어를 다듬고 설계 문서를 만든다. |
| 2 | 설계 검토 | `/plan-ceo-review`, `/plan-eng-review` (또는 둘을 묶은 `/autoplan`) | 계획을 검토하고, 검토 결론을 `decisions.jsonl`에 남긴다. |
| 3 | 구현 | (스킬 없음) | Claude와 함께 코드를 쓴다. 구조, 범위, 도구를 바꾸는 결정은 `gstack-decision-log`로 남긴다. |
| 4 | 코드 리뷰 | `/review` | 계획과 실제를 대조한다. 계획 파일에서 나온 차이를 `learnings.jsonl`에 남긴다. |
| 5 | 출시 준비 | `/ship` | 계획 대조, 테스트, 자체 리뷰, CHANGELOG 조각, TODOS, 문서 점검, 커밋, push, PR을 차례로 한다. |
| 5-1 | (`/ship` 안에서 자동) | `/document-release` | Step 14.5에서 하위 작업으로 실행된다. 직접 부르지 않는다. |
| 6 | (필요할 때) | `/document-generate` | 문서 점검에서 빠진 문서가 많다고 나오면 따로 불러 채운다. |
| 7 | 머지, 배포 | `/land-and-deploy` | 사용자가 직접 입력해서 부른다. |

주의할 점이 있다.
- 3번의 결정 기록은 gstack 스킬이 실행 중일 때 그 스킬의 공통 시작 지침이 Claude에게 시킨다. 스킬 없이 대화만으로 구현하면 자동으로 남지 않을 수 있다.
- `/review`와 `/ship`은 따로 실행하는 스킬이다. `/ship`은 Step 9에서 자체 리뷰를 하지만 `/review` 스킬을 부르지는 않는다. 교훈 기록(순서 4의 파일)은 `/review`에서만 남는다.

## /ship에서 한꺼번에 정리하는 것

후속 질문: "/ship 단계에서 한꺼번에 정리하는 것이 무엇인지 궁금해."

`/ship`은 코드가 다 만들어진 뒤 출시 직전에 한 번 실행된다. 이 시점에 "이번 작업에서 무엇이 바뀌었고, 계획 대비 어떻게 됐고, 무엇이 남았는지"를 최종 코드 기준으로 한 번에 정리한다. 근거: `ship/SKILL.md.tmpl`과 `ship/sections/`의 단계 제목.

| 단계 | 정리하는 것 | 결과가 남는 곳 |
|---|---|---|
| 7 | 테스트 커버리지 감사 | PR 설명 `## Test Coverage` |
| 8 | 계획 대조 (DONE, CHANGED, NOT DONE, 완료 기준 수정 여부) | PR 설명 `## Plan Completion` |
| 9 | 출시 전 자체 리뷰 | PR 설명 `## Pre-Landing Review` |
| 13 | 변경 내용 요약 (사용자 관점) | `changelog.d/<브랜치>.md` |
| 14 | 할 일 목록 (미룬 항목 추가, 끝난 항목은 Completed로 이동) | `TODOS.md` |
| 14.5 | 문서 점검 (`/document-release`가 하위 작업으로 실행) | README, ARCHITECTURE, CONTRIBUTING, CLAUDE.md의 사실 수정, PR 설명의 문서 부채 |
| 15 | 커밋을 논리 단위로 나누기 | git 커밋 |
| 16 | 완료 주장에 새 검증 증거가 있는지 확인 | 통과해야 다음 단계로 감 |
| 17, 19 | push, PR 설명 작성 (요약, 영향 범위, 위 결과 모음) | GitHub |

한꺼번에 하는 이유는 두 가지다.
- 구현 중에는 내용이 계속 바뀐다. 마지막에 한 번 정리하면 최종 코드와 맞는 기록이 남는다.
- 매 출시마다 같은 순서로 빠짐없이 실행된다. 문서 점검은 고칠 것이 없어도 반드시 실행한다("Doc-sync invariant").

반대로 결정 기록처럼 시간이 지나면 이유를 잊어버리는 것은 한꺼번에 하지 않고 행동하는 즉시 남긴다.

## 사용자 상황에 적용할 때

- gstack에서 기록 작업이 몰리는 곳은 "출시 직전" 한 지점(`/ship`)이다. 사용자에게 이에 해당하는 시점은 "개발 완료 후 docx, 위키 작성"이다. 그 시점에 무엇을 모아 정리할지 정하면 흐름을 그대로 빌려 올 수 있다. (결정 현황 D2)
- 결정 기록처럼 "행동하는 즉시" 남겨야 하는 것과 "끝날 때 모아서" 남겨도 되는 것을 나누는 것이 핵심이다.
