# 05. 결정 기록에 JSON 형식을 쓰는 이유

## 질문

결정 기록을 JSON 형식으로 쓰는 이유가 뭔가?

## 결론

결정 기록을 주로 읽는 쪽이 사람이 아니라 **프로그램**이기 때문이다. gstack은 기준이 분명하다. 사람이 읽는 문서(설계 문서, README)는 Markdown으로 쓰고, 프로그램이 읽고 계산하는 기록(결정, 교훈, 질문 기록)은 JSONL로 쓴다.

JSONL(JSON Lines)은 한 줄에 JSON 객체 하나를 쓰는 형식이다. 줄 하나가 기록 하나다.

gstack 문서에 "왜 JSON인가"를 한 문단으로 정리한 곳은 없다. 아래 이유는 코드 주석과 변경 이력(CHANGELOG)에서 확인한 내용이다.

## 근거

### 1. 프로그램이 필드를 읽어 계산한다

근거: `lib/gstack-decision.ts` 첫 주석, `scripts/resolvers/preamble/generate-context-recovery.ts`

기록 한 줄에는 `id`, `kind`(decide/supersede/redact), `supersedes`, `scope`, `branch`, `date`, `confidence` 같은 필드가 있다. 프로그램은 이 필드로 다음 일을 한다.

- **현재 유효한 결정을 계산한다.** `kind`가 `decide`이고, 그 `id`를 가리키는 `supersede`가 뒤에 없으면 유효한 결정이다. 그래서 "유효함/대체됨" 같은 상태 칸을 따로 고칠 필요가 없다.
- **범위별로 거른다.** `gstack-decision-search --scope branch`처럼 이 브랜치의 결정만 찾는다.
- **대화 시작 때 보여 준다.** gstack 스킬이 시작될 때 유효한 결정을 `ACTIVE DECISIONS`로 보여 주고, Claude에게 "이미 정한 것을 말없이 다시 논의하지 말라"고 지시한다.

Markdown 문장으로 적으면 사람은 읽기 쉽다. 하지만 프로그램이 "이 결정이 대체됐는가"를 정확히 판단하기 어렵다.

### 2. 덧붙이기만 하는 기록에 맞다

근거: `lib/gstack-decision.ts` 첫 주석

결정 기록은 기존 줄을 고치지 않고 새 줄만 덧붙인다(append-only). 줄 단위 형식이면 파일 끝에 한 줄을 붙이는 것으로 기록이 끝난다. 주석에는 "고칠 수 있는 status 필드는 덧붙이기만 하는 원칙과 맞지 않는다"고 적혀 있다.

### 3. 여러 에이전트가 동시에 써도 깨지지 않는다

근거: `lib/jsonl-store.ts` 첫 주석

이 파일은 결정, 교훈, 질문 기록이 함께 쓰는 공통 저장 코드다. 주석에 JSONL 저장소가 지켜야 할 세 가지가 적혀 있다.
- 한 줄을 한 번에 덧붙인다. 동시에 실행되는 에이전트가 파일을 망가뜨리지 않게 하려는 것이다.
- 읽을 때 깨진 줄 하나가 있어도 나머지는 읽는다. 쓰다 만 마지막 줄 때문에 전체를 못 읽는 일을 막는다.
- 자유 문장 필드에 숨은 지시문(prompt injection)이 있으면 저장을 거부한다. 기록이 나중에 Claude에게 다시 보여지기 때문이다.

### 4. 여러 컴퓨터의 기록을 git으로 합칠 때 충돌이 적다

근거: `CHANGELOG.md`의 "Two machines that each log a decision between pushes…" 항목

두 컴퓨터가 각자 결정을 기록하고 git으로 합치는 상황이 있었다. 줄 단위 기록(`decisions.jsonl`)은 깨끗하게 합쳐졌다. 반면 JSON 배열 하나로 된 요약 파일(`decisions.active.json`)은 충돌이 났다. gstack은 요약 파일을 합치지 않고, 합쳐진 줄 단위 기록에서 다시 만드는 방식으로 고쳤다. 줄 단위 기록이 원본이고 요약은 거기서 만드는 사본이라는 구조다. (02번의 "원본 하나, 나머지는 생성" 기준과 같다.)

## 사용자 상황에 적용할 때

- 형식을 고르는 기준은 "누가 읽는가"다. 사람이 읽고 다듬을 문서는 Markdown이나 docx가 맞다. 도구가 찾고 걸러야 하는 기록이면 구조화된 형식이 맞다.
- 사용자가 결정 기록을 사람만 읽는다면 JSON이 필요 없다. 표 형식의 Markdown(번호, 결정, 이유, 대체한 결정 번호, 날짜)으로도 "덧붙이기만 하고 대체 표시를 한다"는 원칙은 지킬 수 있다. 이 저장소의 README 결정 현황표가 그런 예다.
